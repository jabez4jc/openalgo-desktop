# 04 - REST API and WebSocket Format Parity: OpenAlgo web vs OpenAlgo Desktop

Date: 2026-10-03
Web (contract source, read-only): `/Users/openalgo/openalgo-desktop/openalgo`
Desktop (implementation under audit): `/Users/openalgo/openalgo-desktop/openalgo-desktop`
Hard requirement: Python SDK, TradingView, Amibroker, Chartink, Excel and MCP clients must work against the desktop with no client changes. Every request and response shape must match the web contract field for field.

All paths below are relative to the two repo roots above unless shown absolute. Line numbers were read from the files on this date.

---

## 0. Verdict in one paragraph

The desktop exposes 34 of the web's 85 `/api/v1` routes on an axum server bound to the same default port (5000) and authenticates the same way (`apikey` in the JSON body). The envelope `{"status": "success"|"error", ...}` is reused, the 403 "Invalid openalgo apikey" path is reused, and the ten simplest endpoints (placeorder, modifyorder, cancelorder, tradebook, positionbook, funds, quotes, analyzer, analyzer/toggle, orderstatus) are wire-compatible or nearly so. However 22 of the 34 implemented routes return a different JSON shape from the documented contract (most commonly wrapping top-level keys inside `data`, renaming keys, or dropping `statistics`/`results`), 5 options routes also reject the documented *request* (string `offset`, `pricetype`), 51 routes are missing entirely, request validation errors come back as axum plain-text 400/422 instead of the JSON envelope, and there is **no inbound WebSocket server at all**: port 8765 is not bound, so the SDK's `subscribe_ltp/quote/depth/orders` and every `/websocket/*` style client cannot connect. The analyzer short-circuit exists for place/cancel/orderbook/tradebook/holdings but not for modify, cancel-all, close-position, positions, funds, openposition or the sandbox execution engine (LIMIT/SL triggering, square-off). Detailed tables follow.

## 3. WebSocket protocol

### 3.1 Web protocol (authoritative: `websocket_proxy/server.py`, `websocket_proxy/mode_utils.py`, `subscribers/wsproxy_subscriber.py`, `docs/prompt/websockets-format.md`, `docs/api/websocket-streaming/*.md`)

Transport
- Plain WebSocket (python `websockets.serve`) on `WEBSOCKET_HOST:WEBSOCKET_PORT` default `127.0.0.1:8765` (`server.py:42`, `server.py:2218-2219`, `.sample.env:101-103`). Control-frame ping every `WS_PING_INTERVAL` 20 s, timeout `WS_PING_TIMEOUT` 20 s (`server.py:200-204`). Behind nginx the public path is `wss://host/ws`.
- One JSON object per text frame. Dispatch key: `action`, falling back to `type` (`server.py:774`). Unknown action -> `{"status":"error","code":"INVALID_ACTION","message":"Invalid action: X"}`; bad JSON -> code `INVALID_JSON` (`server.py:795-800`).
- Error frame shape everywhere: `{"status":"error","code":"<CODE>","message":"...","request_id"?}` (`server.py:1761-1764`). Codes used: `AUTHENTICATION_ERROR`, `BROKER_ERROR`, `NOT_AUTHENTICATED`, `INVALID_MODE`, `INVALID_PARAMETERS`, `INVALID_ACTION`, `INVALID_JSON`.
- Every ack echoes `request_id` when the client sent one (`server.py:1339-1340`, `1663-1664`, `1696-1697`).

Messages (client -> server, then server -> client)

| Client sends | Server replies | file:line |
|---|---|---|
| `{"action":"authenticate","api_key":"..."}` (`apikey` also accepted; `"auth"` alias) | `{"type":"auth","status":"success","message":"Authentication successful","broker":"zerodha","user_id":"...","supported_features":{"ltp":true,"quote":true,"depth":true}}`; failure `{"status":"error","code":"AUTHENTICATION_ERROR","message":"Invalid API key"}` | `server.py:867-1118` |
| `{"action":"subscribe","symbols":[{"symbol":"RELIANCE","exchange":"NSE"}],"mode":1|2|3|"LTP"|"Quote"|"Depth","depth":5|20|30|50,"request_id"?}` (single `symbol`+`exchange` at top level also accepted; `depth_level` legacy alias; mode default `"Quote"`, depth default 5) | `{"type":"subscribe","status":"success"|"partial","subscriptions":[{"symbol","exchange","status":"success","mode":"LTP"|"Quote"|"Depth","depth":<actual>,"broker"} or {"symbol","exchange","status":"error","message":"Depth level 50 is not supported by this broker","broker"}],"message":"Subscription processing complete","broker":"...","request_id"?}` | `server.py:1218-1341` |
| `{"action":"unsubscribe","symbols":[{"symbol","exchange","mode"?}],"mode"?,"request_id"?}` or `{"action":"unsubscribe_all"}` | `{"type":"unsubscribe","status":"success"|"partial"|"error","message":"Unsubscription processing complete","successful":[{symbol,exchange,mode,status,broker}],"failed":[{symbol,exchange,mode|null,status:"error",message}],"broker","request_id"?}` | `server.py:1470-1665` |

Mode normalisation: `1/"LTP"`, `2/"Quote"`, `3/"Depth"` case-insensitive; anything else -> `INVALID_MODE` (`websocket_proxy/mode_utils.py:30-54`). Canonical labels in acks are `LTP`, `Quote`, `Depth`.

Market data frame (server push), one per tick:
```
{"type":"market_data","symbol":"RELIANCE","exchange":"NSE","mode":<client's subscribed mode 1|2|3>,"broker":"zerodha","data":{...}}
```
(`server.py:2116-2146`). A higher-mode broker tick is also delivered to lower-mode subscribers of the same symbol, re-tagged with their mode (`server.py:2097-2100`).
- mode 1 `data`: `{"ltp":1424.0,"timestamp":1756376445123}` (ms)
- mode 2 `data`: `{"ltp","change","change_percent","volume","open","high","low","close","last_trade_quantity","avg_trade_price","timestamp"}`
- mode 3 `data`: `{"ltp","depth":{"buy":[{"price","quantity","orders"}...N],"sell":[...N]},"timestamp"}` where N = requested depth if the broker supports it; supported levels come from the broker capability registry, default `[5]` (`websocket_proxy/mapping.py:70-119`); refusal is per-symbol in the subscribe ack, never a top-level error.


### 3.2 Desktop today

- **No inbound WebSocket server exists.** The only `TcpListener::bind` in the Rust tree is the HTTP server (`src-tauri/src/webhook/server.rs:180`); `tokio-tungstenite` (`src-tauri/Cargo.toml:45`) is used only as an outbound client to broker feeds (`src-tauri/src/websocket/manager.rs:1-7`, `connect_async`). ### 3.3 Drift list (every item blocks the Python SDK streaming API)

1. No server on 8765 -> SDK `connect()` fails. **Must add** a `tokio-tungstenite` accept loop (or axum `ws` upgrade on a second listener) bound to a configurable host:port, default `127.0.0.1:8765`.
2. No `authenticate` handling / `auth` ack; must validate via `sqlite.validate_api_key` and reply with the `type:"auth"` frame including `broker` and `user_id`.
3. No `subscribe`/`unsubscribe`/`unsubscribe_all` with `symbols[]`, numeric or label `mode`, `depth`, `request_id`, per-symbol result arrays, `partial` status.
4. No `market_data` envelope; must wrap ticks as `{"type":"market_data","symbol","exchange","mode","broker","data":{...}}` and shape `data` per mode (strip to `ltp,timestamp` for mode 1; add `last_trade_quantity`, `avg_trade_price`, `change`, `change_percent` for mode 2; `depth.buy/sell` with `orders` for mode 3). Deliver higher-mode ticks to lower-mode subscribers.
5. Mode enum must be 1/2/3 (`Full`=4 and `SnapQuote`=3 are broker-internal; map Angel's SnapQuote->Depth=3 at the adapter boundary).
6. Depth levels 5/20/30/50: per-broker capability table and per-symbol refusal message text `Depth level N is not supported by this broker`.
7. Order update stream: `subscribe_orders` ack and `order_update` frames in the exact key set above, sourced from desktop order placement (live and sandbox) and broker order feeds/polling.
8. `ping` -> `pong` with `server_timestamp`; error frames with `status:"error"` + `code`.
9. Control-frame ping/pong every 20 s; drop subscriptions on disconnect.
10. Depth is never emitted even internally (`manager.rs` emits only `market_tick`), so the UI's own depth view is dead too.

## 5. Analyzer (sandbox) mode

### 5.1 Web
- Single persisted flag `get_analyze_mode()` (`database/settings_db`), toggled by `/api/v1/analyzer/toggle` -> `toggle_analyzer_mode` -> `apply_analyze_mode` under `_MODE_LOCK`, which also **starts/stops the sandbox execution engine and square-off scheduler** and runs missed-settlement catch-up (`services/analyzer_service.py:34-170`).
- Every write service checks the flag first and short-circuits to `services/sandbox_service.py`: `place_order_with_auth` -> `if get_analyze_mode() and not force_live: sandbox_place_order(...)` (`services/place_order_service.py:166-200`); same pattern in smart/basket/split/options/modify/cancel/cancel-all/close-position/GTT services. Read services (orderbook, tradebook, positionbook, holdings, funds, openposition, orderstatus) also read sandbox tables in analyze mode (e.g. `openposition_service.py:109-129`).
- Response shape in analyze: success is the **same** shape as live plus `"mode":"analyze"` (e.g. `{"status":"success","orderid":"26071590395364","mode":"analyze"}`, `sandbox/order_manager.py:129`; `{"quantity":"-10","status":"success","mode":"analyze"}` for openposition; optionsmultiorder results carry `"mode":"analyze"` per leg). Errors: `{"mode":"analyze","status":"error","message":...}` 400 (`place_order_service.py:46-48`, `sandbox/order_manager.py:92`). Sandbox order ids are 14-digit numeric strings. Order updates are published on the `ANALYZE_{user}_orders` topic with `mode:"analyze"`, `broker:"sandbox"` (`wsproxy_subscriber.py:30`).
- `/api/v1/pnl/symbols` is analyze-only (400 in live). 1 Crore sandbox capital, exchange-aligned auto square-off (`CLAUDE.md` Overview).

### 5.2 Desktop
- Flag: `sqlite.get_analyze_mode()` / `set_analyze_mode` (`commands/settings.rs:453-464`; `services/analyzer_service.rs:24-42`). Toggle persists the flag only; no engine start/stop.
- Short-circuit exists in: `OrderService::place_order` -> `place_sandbox_order` -> `sqlite.place_sandbox_order` returning `mode:"analyze"` (`services/order_service.rs:55-59, 281-303`); `OrderService::cancel_order` (`:159-173`); `OrderbookService::get_orderbook/get_tradebook` (`services/orderbook_service.rs:50-53, 83-86`); `HoldingsService::get_holdings` (`holdings_service.rs:35-38`). Smart/basket/split/options reuse `OrderService::place_order` so they inherit the sandbox routing.
- Gaps: `modify_order` in analyze is a no-op success `"Order modified (analyze mode)"` (`order_service.rs:118-126`); `cancel_all_orders` returns empty (`:204-209`); `PositionService` (positionbook, openposition, closeposition) and `FundsService` have no analyze branch (grep finds none in `position_service.rs`, `funds_service.rs`), so in analyze mode positions/funds come from the live broker. Margin is a stub regardless. No execution engine for pending LIMIT/SL/SL-M sandbox orders (web `sandbox/execution_thread.py`), no square-off scheduler, no MTM settlement; `commands/sandbox.rs:81 update_sandbox_ltp` suggests LTP is pushed manually from the UI. REST `placeorder` adds `"mode":"live"` in live mode (web omits `mode` in live).
- Fix: make analyze routing uniform in every service, implement a sandbox execution loop fed by the market tick stream, start/stop it from the toggle, emit `order_update` frames with `mode:"analyze"`, and add `/pnl/symbols`.
